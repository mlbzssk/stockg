# Python 编码规范

## 1. 基本原则

- 优先保证代码正确、清晰、可测试，再考虑抽象和性能优化。
- 遵循 PEP 8、PEP 257 和项目已有代码风格。
- 不保留无效代码、实验代码、注释掉的旧实现或无意义注释。
- 避免无关重构；修改应聚焦当前需求。
- 同一业务逻辑只能有一个权威实现，避免同步、异步或不同模块间复制代码。
- 公共接口变化时，必须同步更新所有调用方、测试和文档。

## 2. 导入规范

- 禁止未使用的导入。
- 禁止 `from module import *`。
- 禁止为了绕过循环依赖而随意在函数内导入；确需延迟导入时应说明原因。
- 导入顺序：Python 标准库、第三方依赖、项目内部模块；不同组之间空一行。
- 优先直接导入实际使用的符号，避免导入整个大型模块。
- 禁止导入实验模块、测试入口或仅在 `if __name__ == "__main__"` 中定义的变量。
- 删除代码后必须检查并删除对应的无效导入和依赖。

## 3. 命名规范

- 模块、函数、变量使用 `snake_case`。
- 类和异常使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 私有实现使用单下划线前缀，如 `_build_graph`。
- 布尔变量使用可读前缀，如 `is_valid`、`has_data`、`should_retry`。
- 名称必须表达业务含义，禁止使用 `data1`、`tmp`、`obj`、`res2` 等模糊名称。
- 避免覆盖 Python 内置名称，如 `list`、`dict`、`str`、`id`、`input`。

## 4. 类型注解

- 新增公共函数、类方法和数据结构必须添加类型注解。
- 使用 Python 3.10+ 类型语法：使用 `str | None`、`list[str]`，不使用 `Optional[str]`、`List[str]`。
- 有限字符串集合使用 `Literal` 或 `Enum`，不要使用无约束的 `str`。
- 禁止为消除类型错误而滥用 `Any`、`cast` 或 `# type: ignore`。
- 使用 `cast` 时，运行时输入必须已经过校验。
- `TypedDict` 应明确必填字段和可选字段。
- 跨模块返回结果优先使用 `dataclass`、`TypedDict` 或 Pydantic Model，而不是无结构字典。

## 5. 函数设计

- 一个函数只承担一个明确职责。
- 函数应尽量短小；出现多个独立处理阶段时应拆分。
- 参数应显式传递，禁止通过可变全局变量或共享 Session 隐式传递业务参数。
- 禁止使用可变对象作为默认参数。
- 返回类型必须保持一致，禁止一个分支返回字典、另一个分支返回字符串。
- 不要创建仅包装一行代码且没有语义价值的函数。
- 参数过多时应考虑封装为不可变值对象。

## 6. 类和数据对象

- 纯数据对象优先使用 `@dataclass`。
- 不需要修改的值对象使用 `@dataclass(frozen=True)`。
- 避免万能类和过大的 Service。
- 依赖通过构造函数或明确参数注入，避免在业务方法中随意创建基础设施对象。
- Domain 层不应直接依赖 FastAPI、数据库客户端或第三方 API 实现。

## 7. 异步规范

- 异步业务链路应以 `async` 作为核心实现。
- 不要同时维护两套完整的同步和异步业务逻辑。
- 同步入口只能作为薄适配器，在最外层调用 `asyncio.run()`。
- 已有事件循环中禁止调用 `asyncio.run()`。
- 异步函数中禁止直接执行阻塞 I/O；阻塞库无法替换时使用 `asyncio.to_thread()`。
- 相互独立的异步任务使用 `asyncio.gather()` 或结构化并发。
- 并行任务禁止修改共享的请求级可变状态。
- 使用锁时，锁内只放必须串行化的操作，禁止在锁内执行不必要的长时间任务。
- 缓存键必须包含所有影响结果的维度，例如 `(market, ticker)`。

## 8. LangGraph 规范

- Graph State 应保存结构化业务字段，不要只拼接一个长字符串。
- 节点必须接收 State，并返回部分 State Update。
- 同一节点的所有分支必须返回相同结构类型。
- `ticker`、`market` 等任务输入应显式存在于 State。
- 不要把不可序列化的客户端、锁、Session 或 Repository 放入 Graph State。
- 图结构固定时应在模块加载或应用启动阶段编译一次，不要每次请求重新编译。
- 确定性操作由普通节点完成，不要为了调用固定工具额外引入 LLM。
- 并行节点写入同一字段时必须配置 reducer。
- Graph 必须有明确的 `START`、终止路径和最大重试次数。
- 需要重试时，重试次数必须写入 State 并设置上限，禁止无限循环。
- 异步节点统一使用 `ainvoke()` 执行。
- Graph 输出应转换为明确的领域结果对象，不应向上层泄漏内部 State。

## 9. 异常处理

- 禁止裸 `except`、空捕获或静默吞掉异常。
- 优先捕获明确异常类型。
- 只有在系统边界或降级节点中才捕获 `Exception`，并说明降级原因。
- 异常信息应包含必要上下文，但不得包含密钥、Token、完整请求头或用户隐私。
- 业务校验失败使用明确异常，如 `ValueError` 或自定义领域异常。
- 禁止通过返回“失败了”等字符串代替所有异常机制。
- 清理 ContextVar、连接和临时资源时使用 `try/finally` 或上下文管理器。
- API 层不得直接向客户端返回内部异常详情和堆栈。

## 10. 日志规范

- 生产代码使用 `logging`，不要使用散落的 `print()`。
- 日志应包含必要的请求标识、任务标识和业务上下文。
- 使用参数化日志，例如 `logger.info("开始股票研究 ticker=%s market=%s", ticker, market)`。
- 禁止记录 API Key、Token、密码、Cookie、认证头、完整个人信息和未脱敏的请求响应。
- 不使用 emoji 作为日志级别或状态协议。
- 异常日志使用 `logger.exception()` 保留堆栈。

## 11. 注释和文档

- 公共类、公共函数和复杂模块应提供简洁 docstring。
- 注释解释“为什么”，不要重复代码表达的“做什么”。
- 删除与实现不一致的过期注释。
- 禁止把大段废弃代码注释后保留在文件中，历史由 Git 管理。
- 文档中描述的参数、默认值和调用方式必须与代码一致。

## 12. 数据与状态管理

- 避免全局可变状态。
- 请求级状态必须隔离，不能被其他请求覆盖。
- 多任务共享数据时应明确并发模型。
- 市场、租户、用户等影响结果的上下文必须显式传递。
- 缓存必须明确 key、生命周期、失效策略和并发安全策略。
- 禁止缓存失败结果，除非有明确的短期负缓存策略。
- 禁止依赖字典字段的隐式存在，应通过结构化类型或显式默认值访问。

## 13. 外部调用

- 所有 HTTP、数据库和第三方 API 调用必须设置超时。
- 重试只适用于幂等操作，且必须设置最大次数和退避策略。
- 禁止无限重试。
- 外部响应永远不可信，必须校验状态码、结构和字段类型。
- SQL 必须使用参数绑定，禁止字符串拼接。
- 密钥只能从环境变量或密钥管理服务读取，禁止写入代码和测试文件。
- 请求用户提供的 URL 时必须防范 SSRF，限制内网地址和不允许的协议。
- 外部失败应返回结构化错误或执行明确降级，不能制造虚假数据。

## 14. 安全规范

- 禁止硬编码密码、API Key、Token 和私钥。
- 禁止使用 `eval()`、`exec()` 处理外部输入。
- 执行系统命令时避免 `shell=True`。
- 必须校验文件路径，防止目录穿越。
- 反序列化外部数据时禁止使用不安全的 `pickle`。
- 输出到 HTML 时必须转义，防止 XSS。
- 权限检查必须在服务端完成，不能只依赖前端限制。
- 错误响应不得泄漏系统路径、数据库结构或内部配置。

## 15. 测试规范

- 修改业务行为时必须补充或更新测试。
- 测试至少覆盖正常路径、参数边界、非法输入、外部依赖失败、异步并发和缓存行为。
- 单元测试禁止依赖真实外部 API，应使用 mock 或 fake。
- 每个测试只验证一个清晰行为。
- 测试名称应描述场景和预期，如 `test_auto_market_resolves_us_stock`。
- 禁止在测试代码中写入真实密钥。
- 修复 Bug 时应先添加能够复现问题的回归测试。

## 16. 代码质量检查

提交代码前至少执行：

```bash
python -m compileall -q stockg
pytest
ruff check .
ruff format --check .
```

若项目使用类型检查，再执行：

```bash
pyright
```

必须满足：

- 无语法错误。
- 无未使用导入。
- 无未定义变量。
- 无明显类型错误。
- 无格式错误。
- 新增和相关回归测试通过。
- 不通过检查时不得用全局忽略规则掩盖问题。

## 17. 禁止事项

- 禁止无效导入和未使用变量。
- 禁止重复实现同一业务逻辑。
- 禁止同步函数和异步函数各维护一套完整流程。
- 禁止裸 `except` 和静默吞异常。
- 禁止无超时的外部请求。
- 禁止无限循环和无限重试。
- 禁止共享可变业务状态导致请求间相互影响。
- 禁止提交调试代码、随机 dummy 数据和临时实验入口。
- 禁止用 `Any`、`type: ignore` 或关闭检查来掩盖真实类型问题。
- 禁止提交硬编码密钥、测试账号和个人数据。
- 禁止仅修改实现而不更新调用方、测试及相关文档。
